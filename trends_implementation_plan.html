3 · The cache — in detail

Clearing up the framing: caching is not something we are adding. TrendService already caches, with a 6-hour TTL. The work is to bound and correct what is there.

3.1 What exists today

Five plain dicts on TrendService, each entry shaped {'data': response, 'ts': datetime}:

CacheKey todayHolds
_minutes_cachewindow_daysMinutesResponse — 527 KB each
_usage_cachewindow_daysUsageResponse — 528 KB each
_regression_cache(window, baseline, mode)RegressionResponse — 217 KB each
_game_log_cache(player, window, baseline, mode)GameLogResponse — 87 KB each
_league_cacheseasonleague pct/usg dict — small

Sizes are measured RSS deltas against live Neon data, 411 qualifying players — not estimates.

3.2 Three defects

① Nothing is ever evicted. _cache_valid checks the TTL when a key is read. If key K is never requested again, K's entry is never examined and never removed. Expiry marks an entry stale; it does not free it. Memory therefore tracks the number of distinct keys ever requested, not the number currently useful. With today's three windows a long session over ~50 expanded players already reaches roughly 78 MB of retained objects on a 512 MB instance. At 56 windows the ceiling is absurd.
② The anchor is not in any key. Every cached value is computed relative to anchor_date = MAX(game_date) from fs_player_games. When last night's ingest lands, the anchor moves — but the keys do not, so stale values keep serving until each entry's own TTL happens to lapse, each at a different wall-clock moment. Two users on adjacent windows can legitimately see different numbers for the same player.
③ _league_cache ignores an input it computes with. _get_league_refs(season, end) aggregates up to end, but caches under season alone. The end argument is not part of the key at all, so once the anchor advances the method returns figures computed against the old end date and has no way to notice. Found while writing this plan; fixed by the same anchor-in-key change.

3.3 What we replace it with

A single small helper class used by all five caches — an OrderedDict with a maximum size and a per-entry expiry timestamp. No new dependency; OrderedDict is stdlib.

get(key) miss -> return None present but expired -> delete entry, return None present and fresh -> move_to_end(key) # mark most-recently-used return value set(key, value) sweep: drop every expired entry # n <= 64, so a full pass is free store (value, now + ttl); move_to_end(key) while len(cache) > maxsize: popitem(last=False) # evict least-recently-used

3.4 How entries actually get cleaned — three mechanisms

You asked how cleaning happens. Three, working together:

MechanismWhen it firesWhat it catches
1Lazy expiry on readSomeone asks for that exact keyStale value for a key still in use. Already how it works today.
2Sweep on writeAny set on that cacheExpired entries nobody will ask for again — the leak today. Bounded at ≤64 entries, so the pass costs nothing.
3LRU evictionlen > maxsizeEntries that are still fresh but least recently used. This is the hard memory ceiling — the guarantee that does not depend on TTL at all.
Mechanism 3 is the one that makes this safe. 1 and 2 depend on time passing and on traffic arriving. LRU is unconditional: the cache cannot exceed maxsize entries no matter what the request pattern is. That is what turns an unbounded structure into a fixed memory budget.

3.5 How long should the TTL be?

Keep 6 hours. The reasoning changes once the anchor is in the key, and it is worth being explicit about why:

  • Freshness is no longer the TTL's job. The anchor is MAX(game_date), itself cached 1 hour (_SEASON_ANCHOR_TTL in player_service.py). When the nightly ingest adds a new game date, the anchor moves within an hour, every cache key changes, and fresh values are computed on the next request. Old-anchor entries become unreachable and are cleaned by mechanisms 2 and 3.
  • So what is the TTL still for? The case the anchor does not cover: a backfill or correction to rows on a date that is already the anchor. Nothing about the key changes, so only the TTL forces a recompute. Six hours bounds that exposure.
  • Why not shorten it? A shorter TTL buys almost nothing — the anchor already handles the common case — and costs real latency, because a miss on the minutes endpoint is 4.4 seconds measured, on a free instance that may also be cold.
  • Why not lengthen it? Nothing to gain. LRU already bounds memory, and 6h keeps the backfill window tolerable.

In short: anchor-in-key handles correctness, LRU handles memory, and the 6h TTL is a backstop for silent data corrections. Three jobs, three mechanisms, no overlap.

The "4.4s cold / 0.5s warm" figures measured cache hits, not misses — _normalize_window_days snapped every supposedly-novel window back to 15, which was already cached. Corrected numbers below, measured against the DB directly with the snap bypassed.

The insightThe expensive work is window-independent; the per-window work is cheap. Caching finished responses per window — what the code does today — caches the cheap part and gets no sharing on the expensive part. Cache the inputs on (season, anchor) instead: ~4 MB, 1–2 entries, reused by every window, preset or custom.

A novel window then costs only the remainder: ~0.50s for Minutes, ~2.07s for Usage. That is acceptable behind an explicit Apply click.

Simpler than proposedInvalidate on anchor change; do not put the anchor in the key. The anchor rotates daily, so anchor-in-key would mint fresh keys every day and orphan yesterday's — which is exactly what forced the LRU in the first place. Instead: store the current anchor on the service; when a request sees a different one, clear the caches and carry on. Key space stays tiny and self-cleaning, with no time dimension to manage.
Prerequisite_game_log_cache needs its cap regardless of any of this. It is keyed by player, so it was never bounded by the window enum, and the player card firing on mount makes it the busiest cache in the service. This is a standalone fix that the dynamic-window question does not touch.
FrontendThe client cache has to be configured for "rely on the frontend" to be true. getTrendsMinutes, getTrendsUsage and getTrendsRegression declare no keepUnusedDataFor, so they inherit RTK Query's default of 60 seconds — a custom window would be re-fetched a minute after you stop looking at it. Raise them to 600s to match getTrendGameLog. One line each.

3.8 Why bound the count at all — and what it does for dynamic windows

Retained for the _game_log_cache case, which still needs a cap. The reasoning below applies to it; §3.7 supersedes it for the window-keyed caches.

The core pointThe (7, 15, 30) enum has been acting as your cache bound. Three legal windows meant _minutes_cache could never hold more than three entries — not by design, but as a side effect. That is why no eviction policy has ever been needed. Dynamic windows delete that accidental bound, so an explicit one has to replace it.
CacheMax entries todayMax entries at 56 windowsMemory unbounded
_minutes_cache35629 MB
_usage_cache35629 MB
_regression_cache1833673 MB
_game_log_cache18 × players336 × playerseffectively unbounded

On a 512 MB instance.

maxsize counts entries, not bytes. maxsize = 8 means eight cached responses. The numbers in §3.6 were chosen by multiplying entries × measured bytes-per-entry to reach a memory budget — the cap is expressed in items, the reason for each cap is bytes.

What bounding actually buys — stated honestly

It does not make dynamic windows faster. It trades a small, occasional performance cost for a hard memory guarantee. A worked example, with the caps from §3.6:

cap = 8 on _minutes_cache you try 15d, 7d, 30d, then custom 21d, 10d, 45d -> 6 entries, all warm teammate tries 12d, 18d, 23d -> cache reaches 8, then evicts 45d (least recently used) anyone asks for 45d again -> 4.4s recompute, not instant memory throughout: 8 x 527 KB = 4.2 MB, flat
  • Unbounded: always fast, memory grows with every distinct parameter set ever requested, can exhaust the instance.
  • Bounded: memory fixed at the cap, occasional recompute for parameters nobody is actively using.

With roughly a dozen users the actively-used working set sits well below the caps, so evictions should be rare in practice. If they are not, each cap is a single constant to raise — the memory cost of doing so is exactly linear and known.

P1Hoist inputs, invalidate on anchor, cap the game-log cachebackend · blocker · ships alone
Why
Fixes the three defects in §3.2 and makes every window cheaper, per the revised §3.7. Required before any window-space expansion, and valuable without it.
Shape
Cache the expensive window-independent inputs; leave the cheap per-window work uncached; cap only the one cache that is genuinely unbounded.

Changes

  • (a) Hoist the window-independent frames into caches keyed (season, anchor): the season-to-date aggregate_shooting_by_player (0.63s, 0.07 MB), get_usage_components (0.90s, 3.80 MB), and the prior-seasons baseline. Every window reuses them. This is the single biggest win — it cuts ~1.5s off every miss.
  • (b) Anchor-change invalidation. Store the anchor on the service; when a request observes a different one, clear the caches. Replaces both anchor-in-key and TTL-driven cleanup for the small caches, and fixes defect ② and defect ③ (_league_cache ignoring end) at once.
  • (c) Cap _game_log_cache. TTL+LRU helper per §3.3, cap 64 (≈5.6 MB). This is the only cache keyed by player, so the only one the window enum never bounded.
  • (d) Response caches stay preset-only. _minutes_cache / _usage_cache / _regression_cache cache 7/15/30 as today. Custom windows skip the response cache and compute fresh.
  • TTL stays 6h where it still applies, as the backstop for silent backfills (§3.5).

Tests

  • Hoisted frames are computed once and reused across several different windows (assert one DB call, not N).
  • A changed anchor clears the caches and recomputes; _get_league_refs returns different results for two anchors.
  • _game_log_cache: eviction past maxsize, LRU ordering, TTL expiry on read, sweep on write.
  • A custom (non-preset) window does not populate the response caches.

Verify

  • Request across 60 distinct window values; assert response-cache length stays at the preset count, _game_log_cache stays at its cap, and RSS plateaus rather than climbing.
  • Time a novel window before and after the hoist — expect ~1.5s saved.
P2In-flight request coalescingbackend
Why
More distinct windows means more simultaneous misses. Also matters for the player card, which fires on every profile view.

Changes

  • A dict[key, asyncio.Future] beside each cache. First caller creates the future and computes; concurrent callers on the same key await it instead of issuing their own query.
The one gotchaClear the future in a finally, never only on success. If a query raises and its future is left in the dict, every later caller awaits a permanently-failed future and the endpoint stays broken until the process restarts. Waiters receiving the exception is correct — they would each have failed anyway — but the slot must be freed either way.

Tests

  • N concurrent callers on one key produce exactly one DB call.
  • A raising computation propagates to all waiters and clears the slot, so the next call retries cleanly.

  • P1 first, always. It fixes a live memory risk and is a prerequisite for P3. Nothing else should land before it.
  • P0 and S1–S3 are independent of the backend track and of each other; either can go in parallel.
  • S1–S3 can ship with fixed 7/15/30 presets and adopt the picker later in S4. The player card does not have to wait for the dynamic-window work.
  • Per CLAUDE.md: branch off fresh dev, PRs target dev, never master. The pre-push hook runs tsc --noEmit on frontend changes.

7 · What we are not doing

  • No arbitrary start/end range on trends. The end stays pinned to the anchor — otherwise the Form tab's table baseline (season − window) and its chart baseline (game_date < window_start) diverge silently.
  • No expanded-presets shortcut. Ruled out; going to the full picker.
  • No changes to the Players list page. Its two-date custom range is correct there — it aggregates, it does not compare.
  • No days ⇄ games toggle. Needs a per-player window instead of one global date, touching every compute function. Separate feature.
  • No new backend endpoint for the player card. Option A derives everything from the existing game-log response.
  • No role badge or z-score on the player card. Same decision — avoids duplicating Python thresholds in TypeScript.
