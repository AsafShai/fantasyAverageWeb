2 · Independent, non-blocking load per your ask

Agreed, and it matters more than it first looks. Three separate reasons, in increasing order of severity:

  1. The endpoint is genuinely slow on a miss. /trends/player/{id}/gamelog runs a multi-join query over fs_player_games + fs_team_games, then _prior_shooting across up to two prior seasons, then _get_league_refs which aggregates every player's shooting and usage for the season. The result is cached 6h — but the first caller after a restart pays all of it.
  2. Render free tier sleeps after ~15 min idle. A cold start means the container boots, and on this app boot also kicks off the injury-PDF fetch and scheduler setup before serving. Blocking the profile on that turns a 300ms page into a 30s+ page.
  3. It can 404 legitimately. A player with no fs_player_games rows this season returns 404 by design. If that sits on the page's critical path, a perfectly valid player page shows an error.
ResolvedThe page already works this way — just don't break the pattern. PlayerProfile.tsx today blocks only on the bio query (if (bioLoading) return <LoadingSpinner /> at line 85), and the bio comes from a static JSON catalog held in memory — nba_player_catalog.py reads nba-players-2025-26.json once and caches it, no DB, no external call. Stats already render their own spinner inside the Stats card. The Trends card follows that same shape.

Rules for the implementation

  • Own query, own state. Put useGetTrendGameLogQuery inside the card component. RTK Query gives it independent isLoading/error by construction — nothing is shared with the bio or stats queries.
  • Never touch the early return. The bioLoading / bioError guard at the top of PlayerProfile stays exactly as it is. No trends state joins it.
  • Skeleton, not a spinner — and reserve the height. The card is ~320px tall when loaded. A collapsing spinner makes the page jump when data lands. Render a fixed-height skeleton so nothing below it moves.
  • Lazy-fetch on visibility. The card sits below the fold on most screens. Gate the query on an IntersectionObserver (or the card's expanded state) via RTK Query's skip, so a user who never scrolls never pays for it — and a cold backend is not woken by every profile view.
  • Isolate the failure. 404 → "No game log this season" inside the card. 500 / timeout → a small retry line inside the card. Neither may render ErrorMessage at page level.
  • Don't refetch on window focus for this one — the underlying data is on a 6h server cache, so refetching on every tab focus is pure cost with no freshness gain.
DecidedFetch timing: fire on mount. The alternative was lazy-on-visibility and "appears when ready" pull in slightly different directions: if the user scrolls straight down, the fetch starts when they arrive, so they watch the skeleton for the full cold-start duration instead of it having loaded in the background. Options: (a) fire the query immediately on mount but keep it non-blocking — simplest, costs one request per profile view; (b) lazy on visibility with a generous rootMargin (~600px) so it starts fetching just before it scrolls into view. Recommend (b) — it gets the head start without waking the backend for users who bounce off the page.

Why not call the list endpoints? /trends/minutes, /trends/usage and /trends/regression return the whole league and are threshold-gated — a player who has not moved (or who fails MIN_SEASON_GP = 10, or the drift_score ≥ 0.35 / |z| ≥ 1.5 gates) has no row at all. On a player page every player must render something, so the gates are wrong here. Pulling a ~500-player payload to find one row is also wasteful on a free instance.
Decided → ADuplicated-formula risk. Deriving the role badge and z in TypeScript duplicates Python thresholds. If one moves, the player page silently disagrees with the Trends table.
  • A (recommended): derive only the uncontroversial numbers client-side — window averages and Δ. Nothing to drift. The demo above does exactly this: it shows Δ and game counts, no badge, no z.
  • B: add GET /trends/player/{id}/summary running the same Python helpers ungated for one player. One thin route + service method; single source of truth. Do this only if you want the badge and z on the page.

5 · Edge cases the card must handle

  • 404 — no fs_player_games rows this season (two-way, G-League, injured all year, offseason signing). "No game log this season", inside the card. Demo it with the 🚫 button.
  • Rookie / no prior seasons — baseline_pct comes back empty, so the shooting chart has no baseline line. Confirm it degrades cleanly rather than drawing a line at 0.
  • Very few games in window — below 3 games the Δ is noise. Grey the Δ tile and show the game count, matching the Trends page's partial badge at LOW_SAMPLE_GP = 3. Try the 7d window in the demo.
  • Zero attempts for a stat — hide that mode chip rather than plotting a flat 0 (a centre with no 3PA).
  • Baseline choice — do not expose the 0/1/2 prior-seasons picker here. Pin it and keep the surface small.

7 · Shooting baseline — decided

Decided → form / 0mode=form, baseline_seasons=0. The plan said "pin them and keep the surface small" without saying to what — and the choice is visible, because it changes the baseline reference line the chart draws:
  • mode=season + baseline_seasons=2 → baseline is prior seasons only. Answers "is this season out of step with his career". Steady line, slow to react to a genuine change in the shooter.
  • mode=form + baseline_seasons=0 → baseline is this season outside the window. Answers "is he hot or cold right now relative to himself". Follows a player whose level has actually moved.
Recommend form / 0. A player page is read to answer "how is he doing lately", which is the form question — and it is the only one of the two that stays meaningful for a rookie, where the season-mode baseline is empty and the chart draws no line at all. The Trends page keeps both because it has a tab per question; the player card should not grow a tab bar for this.
The window control here should match whatever ships on the Trends page — see trends_dynamic_range_plan.html. Presets plus an optional start-date custom, end always pinned to the anchor.
