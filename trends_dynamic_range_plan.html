The real findingThe cache is already a memory risk today, before any of this ships. _game_log_cache is keyed (player_id, window, baseline, mode) and never evicts. With today's 3 windows that is still 3 × 3 × 2 = 18 entries per player — a session where someone expands 50 players across a few settings reaches ~78 MB of retained pydantic objects on a 512 MB Render instance. Open the window space to 56 and the theoretical ceiling is ~14 GB.

3 · Which control — reuse the existing date picker

"Last N days" and "a start date" are the same control. With the end pinned to the anchor, window_days = anchor − start — same request, same maths, same cache key. The choice is presentational only, so the two framings coexist rather than compete:
  • Presets (7 / 15 / 30) = count-thinking. "How has he looked the last two weeks." The common case, one tap, no arithmetic.
  • Custom date = event-thinking. "Since the deadline", "since he came back from the ankle". This is why anyone reaches past the presets, and for that intent a date is exactly right — a count would force the user to work out what was 23 days ago.
A bare number box serves neither: presets beat it for the common case, a date beats it for the deliberate one. Hence presets + start-only picker, with the derived = 21 days always on screen so the trends semantics stay legible.

DecidedThe end date is not user-editable here. DateRangePicker as it exists takes a free start and end. A trends window must always end at the anchor date (§4①) or Shooting · Form's table and chart baselines silently diverge. So the reuse is start-only: pass end pinned to the anchor and render it disabled, then convert window_days = anchor − start before calling the API. The backend contract does not change — it still receives an integer.
Decided → P5Anchor ≠ today. DateRangePicker defaults its today prop to new Date(). The trends anchor is the latest game day in the data, which lags today whenever no games have been played yet today — and lags it by months in the offseason. Pass the anchor explicitly, and word the panel "through Feb 7 (latest game day)", not "through today". It is available on every trends payload as window_start + window_days, or from useGetLeagueSummaryQuery.
Decided → P3Timezone: never round-trip these dates through toISOString(). Found while building the demo above — the anchor rendered as Feb 6 instead of Feb 7. new Date('2026-02-07T00:00:00') is local midnight, and toISOString() converts to UTC, which in Israel (UTC+2/+3) lands on the previous day. Every date that crosses the boundary here is affected: the value fed to <input type="date">, the min/max attributes, and the window_days subtraction — a silent off-by-one that shifts the whole window and is invisible until someone checks the game count.

Build the YYYY-MM-DD string from getFullYear/getMonth/getDate, and do the day-count subtraction on dates normalised to local midnight.

4 · Problems with the idea — read before building

Decided① Why the end is pinned: an arbitrary start/end would make the table and the chart disagree. If "dynamic" means picking any two dates, Shooting · Form develops a silent inconsistency:
  • _form_stat (the table) builds the baseline as season_totals − window_totals — everything outside the window, including games after it.
  • _form_baseline_pct (the chart's reference line) builds it as games_df[game_date < window_start] — strictly before the window.
These are identical today only because the window is always a trailing suffix of the season. Give it a mid-season range and the same player shows one baseline in the row and a different one in the expanded chart, with nothing erroring.

Correction to an earlier draft: the two-proportion z-test itself stays valid — season − window is set-disjoint from the window wherever it sits. The problem is the two divergent baseline constructions, not the statistics.

Decision: end always pinned to the anchor. A true start/end range would need the two baseline paths unified first, and belongs in its own tab — the "Δ vs season" framing on Minutes and Usage also assumes a window that ends at the present.
Decided → P1② Unbounded caches become a leak. Four dicts keyed partly by window_days, none of which ever evict — entries are only TTL-checked when read. Today the key space is 3 values. Open it to 56 and _game_log_cache alone becomes players × 56 × 3 baselines × 2 modes of retained GameLogResponse objects on a Render free instance. Must ship together with bounded caches (an OrderedDict LRU, maxsize ~64 per cache, plus an expired sweep on write). Prerequisite, not a follow-up.
Decided → P6③ Small windows collide with fixed sample gates. MIN_WINDOW_GP = 2 and LOW_SAMPLE_GP = 3 are absolute game counts. At 5–7 days nearly every qualifying player sits at 2–3 games, so Minutes Movers becomes a wall of partial badges and Δ is mostly noise. Form mode is safe — its |z| ≥ 1.5 gate self-calibrates and simply returns fewer rows. Mitigation: the live "N game nights" hint plus an inline caution below ~10 days. Drag the demo below 10d to see it.
Decided → P6④ The control is prominent on a tab where it barely does anything. On Shooting · Season the window only drives the G(Nd) column; the actual comparison is season vs prior seasons. Making the control bigger makes that mismatch more confusing. Mitigation: on that tab, de-emphasise it and retitle to Activity window with a tooltip saying it only filters by recent games played.
⑤ Days is arguably the wrong unit. A 15-day window is 4 games for one player and 8 for another. For judging form, "last N games" is more natural. Days is right for "what changed since the deadline"; games is right for "is he hot". Ship days first — it is what the pipeline already speaks — and treat a days ⇄ games toggle as a distinct later feature: it needs a per-player window instead of one global date, which touches every compute function.

8 · Gaps found on review

Decided → P2 (coalesce)① Thundering herd on a cold instance. Today only three windows exist, so the caches are warm almost all the time and a cache miss is rare. Open the key space to 56 and a just-woken instance can take several users on different windows at once — each firing its own season-wide aggregate_shooting_by_player with none of them able to reuse the others' work. The 6h TTL does not help; they all miss simultaneously.

Options: (a) coalesce in-flight requests — keep a dict[key, asyncio.Future] beside each cache so concurrent callers on the same key await one query; (b) accept it, on the grounds that this is a ~12-user private league and simultaneous distinct-window cold hits are unlikely. (b) is defensible — but decide it deliberately rather than discovering it under load, and note that (a) is ~15 lines and also protects the existing 3-window case.
Decided → P1 (anchor in key)② Cache staleness surface grows. Not a new bug, but worth naming: the 6h TTL means a window can serve data that predates last night's ingest. With 3 windows that is 3 stale surfaces; with 56 it is up to 56, each expiring at a different wall-clock time, so two users on adjacent windows can legitimately see different numbers for the same player. If that is unacceptable, key the caches on the anchor date so an ingest that moves the anchor invalidates everything at once — a one-line change to the cache key, worth doing while the caching code is already open.

9 · Interim plan, item by item

Each is independently shippable and independently revertable. Order matters only where stated.

P1 · Bounded caches backend · blocker · ships alone

  • Add a small _TTLCache helper in trend_service.py: OrderedDict, get/set, move_to_end on hit, popitem(last=False) past maxsize, TTL checked on read and swept on write.
  • Replace the four plain dicts. Caps: minutes 8, usage 8, regression 12, game-log 64 (→ ~17 MB ceiling, per §0b).
  • Include the anchor date in every cache key (the §8② decision) — one tuple element, so a new ingest invalidates all four caches at once instead of each aging out separately.
  • Tests: eviction past maxsize, TTL expiry, LRU ordering, and that a changed anchor misses.
  • Verify: hammer one endpoint across 60 window values, assert len(cache) stays at the cap and RSS plateaus.

Ships regardless of everything else — it fixes a live memory risk on its own.

P2 · Request coalescing backend

  • dict[key, asyncio.Future] beside each cache. First caller creates the future and computes; concurrent callers on the same key await it.
  • The one gotcha: remove the future in a finally block, not on success. If a query raises and the future is left in the dict, every later caller awaits a permanently-failed future and the endpoint stays broken until restart. Waiters correctly receive the exception — they would each have failed anyway — but the slot must be freed.
  • Tests: N concurrent callers on one key produce exactly one DB call; a raising computation propagates to all waiters and clears the slot so the next call retries.

~15 lines. Also protects today's 3-window case, so it is not purely dynamic-range work.

P3 · Timezone helpers frontend · independent

  • utils/dateRange.ts: add toLocalIso(date) and daysBetween(startIso, endIso); rewrite todayIso() on top of toLocalIso.
  • Repoint the 4 sites listed in §3 — dateRange.ts, DateRangePicker.tsx, Analytics.tsx, Rankings.tsx.
  • Vitest with TZ forced to a non-UTC zone, asserting local midnight does not roll back a day.
  • Verify: the existing Analytics/Rankings preset buttons still produce the same ranges outside the 00:00–03:00 window (no regression), and the correct ones inside it.

Pre-existing bug in shipped pages — worth doing on its own branch, before any trends work.

P4 · Clamp instead of snap backend

  • VALID_RECENCY_WINDOWS_DAYS → MIN_RECENCY_WINDOW_DAYS = 5 / MAX_RECENCY_WINDOW_DAYS = 60. _normalize_window_days clamps. Single consumer, confirmed by grep.
  • routes/trends.py: Query(DEFAULT, ge=5, le=60) on all four routes so bad input 422s at the edge.
  • Tests: clamping at both ends; a window outside the old triple is honoured rather than snapped to 15.
